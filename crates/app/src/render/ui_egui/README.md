# crates/app/src/render/ui_egui

## Purpose
This directory adapts the experimental egui frontend crate into Pentimento's
Bevy application lifecycle.

## Contents
| File/Folder | Description |
|-------------|-------------|
| `mod.rs` | Plugin wiring and schedule registration for the egui frontend path. |
| `resources.rs` | Bevy-owned resource wrapper around the egui snapshot/runtime state. |
| `ipc_handler.rs` | Backend-to-egui snapshot synchronization and UI command dispatch. |
| `render.rs` | Per-frame egui rendering entrypoint that invokes the UI crate facade. |

## Problem
The application crate needs a thin orchestration layer for egui that preserves
the existing composition-root boundary instead of letting egui runtime details
spread into generic render or scene modules.

## Constraints
- Must keep egui-specific rendering and input ownership out of the generic
  capture-based frontend pipeline.
- Must consume `crates/ipc` messages instead of defining a parallel contract.
- Must remain additive so existing Dioxus, CEF, and Electron entrypoints are
  not broken by the experimental egui path.

## Decision
Mirror the `ui_dioxus` adapter pattern with a smaller egui-specific directory
that owns resource setup, outbound message ingestion, and per-frame rendering.

## Alternatives Rejected
- Wiring egui directly in `render/mod.rs`: rejected because it would grow the
  composition root with framework-specific state handling.
- Reusing the capture-based `FrontendResource` path: rejected because egui is a
  Bevy-native UI integration, not a webview backend.

## Invariants
- The Bevy app remains the single lifecycle owner for egui state resources.
- Shared UI/backend commands still use `crates/ipc` enums.
- The presentation facade requests initial brush/document snapshots and returns
  accepted-state commands; this adapter dispatches through the shared scene owner.
- Every frame publishes actual egui panel and floating popup rectangles in window
  logical coordinates. Native forwarding latches a UI-origin press through release,
  including a stationary press. Startup waits for egui's own layout, and document
  modals capture the whole viewport and block scene keyboard input.
- CEF/Electron/Dioxus transport and geometry/history algorithms remain independently
  owned. A passing headless widget/controller test is not native renderer validation.

## Revisit Triggers
- The egui path gains enough complexity to justify subdirectories by panel or
  workflow.
- Shared UI message handling is extracted into a frontend-agnostic application
  service.

## Dependencies
**Internal:** `crates/app/src/render`, `crates/egui-ui`, `crates/ipc`, `crates/scene`  
**External:** `bevy_egui`

## Related ADRs

## Usage Examples
```rust
app.add_plugins(ui_egui::EguiRenderPlugin);
```

## API Consumer Contract
- Consumed only by `crates/app/src/render/mod.rs`.
- Callers select this plugin by choosing `CompositeMode::Egui`.
- The plugin owns egui resource creation and frame rendering for the app.

## Structured Producer Contract
- Produces in-process `UiToBevy` command dispatches only.
- Inbound/outbound message semantics must stay aligned with `crates/ipc`.
- No persisted artifact is generated by this directory.

## Remaining Input Qualification
This source milestone includes real history buttons and acknowledged availability.
Fresh text-field focus and a history shortcut arriving in the same native event
batch remain an integration limitation. An app-owned ordered Canvas/DirectUV fix
and real-field regressions are preserved separately pending execution; their
controller rebuild exhausted disk before running. Sculpt's raw keyboard history
consumer also needs the scene owner's ordered-input integration. These limitations
prevent claiming complete native keyboard/history parity or native GUI validation.
